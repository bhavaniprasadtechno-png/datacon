# 01 — Predictive Agent Migration: forecast with structured facts and a real confidence band

**What to build:** The complete "forecast X" product behavior, end to end, through the shared pipeline: the existing forecast computation (unchanged) → validated structured facts → KPI metrics for projected/CI/growth → a Planner-selected line chart with the confidence band attached → MAPE-based confidence → correct rendering in the running UI, with no regression to Descriptive. This replaces today's bespoke, agent-local chart/table payload. One vertical slice — backend and frontend are not split into separate tickets.

**Blocked by:** `01 — Visualization Registry: extensible Planner + renderer architecture, with line as the first type` (`.scratch/visualization-registry-line-type/issues/01-...`). Does not depend on the payload-adapter prefactor ticket — Predictive has no citations/escape-hatch fields at all; its migrated payload is purely the new structured shape.

**Status:** done

- [x] Forecast computation itself (Holt-Winters model, 6-month horizon, MAPE-based confidence thresholds) is byte-for-byte unchanged — this ticket restructures the output shape only.
- [x] Projected value, CI low, CI high, and growth % become headline KPI metrics; MAPE does not become a separate metric.
- [x] The historical-plus-forecast series renders as a `line` visualization via the Registry's rule, with the confidence band (`lower`/`upper`) attached to the final data point exactly as today's pre-migration chart already does — verified by test assertion on the band values, not just that a line renders.
- [x] The table reflects only the real historical query rows (month, revenue) — the synthetic "forecast" row today's pre-migration table appends is dropped.
- [x] Confidence is computed by Predictive directly from MAPE (`<15% high / <30% medium / else low`, unchanged thresholds) and placed directly into the response's confidence field — not routed through the Validator (Predictive doesn't call `validate()` at all, consistent with "no structural concerns beyond what the Planner/contract already guarantee" for this agent's simpler shape).
- [x] A true-empty state (insufficient revenue history) returns a real `StructuredResponse` with `confidence: low` and empty metrics — covers both "nothing connected" and "connected but only 1 data point" branches.
- [x] The dataset-name-inference **and** row-sanitization helpers currently local to the Descriptive agent module are extracted into a shared location (`app/pipeline/normalizer.py`: `infer_dataset_name`, `humanize_dataset_name`, `sanitize_rows`) — not duplicated. Reuse in practice: Predictive uses all three (it infers/humanizes a real dataset name from its SQL); Diagnostic and Prescriptive use only `sanitize_rows` (both use a fixed subject label instead of inferring one from SQL, so `infer_dataset_name`/`humanize_dataset_name` have no caller yet outside Descriptive and Predictive — code-review caught an earlier, inaccurate version of this note that claimed Diagnostic used all three). Descriptive's own behavior and existing tests are unaffected by the move — full suite confirms. New direct unit tests added for all three extracted functions in `test_normalizer.py`, including the hyphenated-identifier and connector-prefix edge cases.
- [x] Integration test against the same DuckDB-fixture + mocked-SQL-generation seam as prior deliveries — 4 scenarios in `test_agents.py`: high-confidence forecast (low MAPE, asserted `== "high"`), lower-confidence forecast (volatile data, asserted `in ("medium", "low")`), no-data-connected, and insufficient-history (1 row).
- [x] Verified live in the running app: asked "Forecast revenue for the next two quarters" against the real running dev stack — real date labels (not "p0,p1..."), KPI cards for Projected/95% CI/Growth, line-plus-band chart, "High confidence" label, table with real month/revenue rows and no synthetic forecast row. (A local dev-environment process bug initially masked this — see Diagnostic ticket's note — root-caused and fixed via `diagnosing-bugs` before this check could actually be trusted.)
- [x] Full test suite remains green: 164 passed, 3 pre-existing unrelated failures in `test_generator.py`.

**Known minor gap (not in scope):** the KPI metric cards use `format: "currency"` (renders `$4.84`), while the chart's own stat row keeps its existing `formatMillions` treatment (renders `$4.84M`) — a small cosmetic inconsistency inherited from the fact `MetricFormat` has no "millions" variant. Not addressed here since it wasn't part of the ticket's acceptance criteria.
